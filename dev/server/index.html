Engine server and RPC¶

crates/v2xw-server serves one run (live from the engine, or the synthetic fixture) to browsers, notebooks and scripts: the binary VWP stream over a WebSocket and a JSON-RPC 2.0 control surface over the same socket and over HTTP. The normative wire specification is VWP v1; this page is the developer's map of it, with every method of v2xw_server::rpc::METHODS.

Starting a server¶

Command Serves
v2xw-server --scenario <file> a live engine run of the scenario, with the agent's endpoints and watcher
v2xw-server (no --scenario) the synthetic fixture: a deterministic procedural grid with --actors, --grid, --block, --duration, --seed; every number it reports is a fixture value
v2xw serve --scenario <file> the same live run with the agent's endpoints, through the main CLI
v2xw serve --attach <url> only the agent's endpoints, in front of an engine already running
just serve <scenario> / just serve-fixture [ACTORS] the two above on port 8787
./run-sim.sh [scenario] builds if needed and starts the engine with the agent on

v2xw-server options:

Option Default Meaning
--scenario <p> none (fixture) scenario to run
--record <p> none write the MCAP recording here
--build-utc <t> now, read by the binary manifest timestamp (the engine reads no clock)
--retain <n> / --retain-mb <n> 36000 steps / 1024 MB history kept for run.seek
--lookahead <n> 64 steps the kernel may run ahead of the stream
--resume <p> none open a v2xw run --checkpoint-every run at its checkpoint.json and serve it paused there
--port <n> 8787 TCP port; 0 picks an ephemeral one
--host <addr> 127.0.0.1 bind address; a non-loopback bind needs --token
--token <t> none bearer token required on the upgrade and on every HTTP request
--speed <x> 1 multiple of real time; 0 is unthrottled
--paused off start paused at t = 0
--label <s> human label in Hello
--no-agent off serve without the agent's endpoints and watcher
--env-file <p> ./.env when present where the agent's model-provider keys are read from
--quiet off no banner

From Rust: v2xw_server::serve_scenario(ServerOptions, path, LiveOptions), serve_stub(ServerOptions, StubOptions) and serve_replay(ServerOptions, recording, world, world_json) each return a running VwpServer. ServerOptions { bind, token, extension } takes an extra axum::Router merged on the same origin, which is how the agent's routes are added. No shipped binary serves a replay; the Studio replays recordings in the browser through v2xw-wasm (Recording format).

Transports¶

flowchart LR
    subgraph Server["v2xw-server (one run)"]
        E["Engine trait<br/>LiveEngine / StubEngine / ReplayEngine"] --> R[Run]
        R --> WS["GET /vwp/v1<br/>WebSocket"]
        R --> RPC["POST /rpc"]
        R --> W["GET /world/{hash}.vwb|.json"]
        R --> S["GET /rpc/schema"]
        R --> H["GET /healthz"]
        A["/agent/* (v2xw serve, v2xw-server)"]
    end
    WS -- "binary: VWP frames" --> C[Studio / client]
    WS -- "text: JSON-RPC + notifications" --> C
    RPC --> N[CLI, notebook, CI]
Endpoint Purpose Spec
GET /vwp/v1?run=&session=&resume=&profile=full\|node&compress=zstd\|none&v=1 WebSocket, subprotocol vwp.v1. Binary frames carry the stream; text frames carry JSON-RPC §1.1, §1.2
POST /rpc the same methods, one call per request; connection-scoped methods return -32009 §6.2
GET /rpc/schema the OpenRPC 1.3.2 document (rpc.discover's result) §6.3
GET /world/{hash}.vwb, .json the world geometry, vwp-world/1, content-addressed and immutable §4
GET /healthz liveness §1.1

Every response carries the cross-origin isolation headers (Cross-Origin-Opener-Policy: same-origin, Cross-Origin-Embedder-Policy: require-corp, Cross-Origin-Resource-Policy: same-origin). A missing or wrong bearer token is HTTP 401, never a WebSocket close.

Stream topic Spec
handshake (Hello), reconnect and resume by session token and seq §1.3, §1.4
backpressure: bounded queues, drop policy, stream.drop §1.5
24-byte frame header, flags, message types, symbol table, compression §2
Hello, Keyframe, Delta, Telemetry, Event, MetricSample, Provenance, WorldChunk, Error, Bye §3
full and node visibility profiles §5
replay, byte identity, seek §7
versioning §8

Every frame the server sends is built by v2xw-record's encoder (v2xw_record::wire); only the connection-scoped Error and Bye frames are written in http.rs.

JSON-RPC conventions¶

  • JSON-RPC 2.0, single objects only (a batch array is refused with -32600); params by name. §6.1
  • Long operations return a Job ({job_id, state, progress, message, outputs}) and finish with job.progress / job.done notifications.
  • rpc.discover (or GET /rpc/schema) returns every method's params schema, result schema and error list; the shared schemas (SimTimeNs, RunId, NodeId, Sha256Hex, ValueRef, Provenance, ValidationError, WorldImportResult, Job) are in §6.5.
  • Times are integer nanoseconds since the scenario's time.t0.

Methods¶

METHODS holds 44 names; the client list in ui/packages/protocol/src/rpc.ts is held equal by crates/v2xw-server/tests/rpc.rs. In the tables, a bold param is required; results list the main fields (required ones in bold). "Spec" links the method's section in VWP v1 where it has one.

This build's server refuses every scenario.save with -32013 (EROFS): it writes nothing outside a recording path the operator named. Save from the client, or with v2xw validate and a file editor.

On a live run, export.recording copies the run's recording (started with --record) to path in the full profile; any other profile returns -32009. export.dataset returns -32008: dataset writers run as part of v2xw run, through the scenario's exporters list (Datasets and exports).

Notifications¶

Server to client, never requests (§6.14):

Notification When
run.state the run's state changes
stream.drop backpressure dropped frames for this connection
job.progress, job.done a long operation progresses or ends
view.changed the connection's view changed
log a server log line
validation validation results for a staged scenario
experiment.progress an experiment's progress
node.feed the followed node's messages and queues, while a view.follow {feed} stands

Agent endpoints¶

Served on the same origin by v2xw-server and v2xw serve unless --no-agent is given (then only GET /agent/status answers, with available: false). The agent reaches the engine through the same JSON-RPC as any client, so it has a Studio user's authority. Model keys stay in the server process (read from the environment or --env-file) and are never returned. See Assistant.

Endpoint Does
GET /agent/status whether a model is attached, which one, where its key comes from (named, never shown)
POST /agent/ask {prompt} starts the agent on a prompt; follow-ups continue the conversation
POST /agent/run {base} runs a shipped scenario and analyses it, no model needed
POST /agent/analyse analyses the run on screen, no model needed
GET /agent/events?job=&after= a job's events from after: plan, changes, progress, analysis, report
POST /agent/stop stops the job at its next check, pausing a run it started
POST /agent/reset forgets the conversation
POST /agent/undo {setup} gives the settings window back what it held before that setup
GET /agent/watch?after= the always-on watcher: what it noticed about the runs since after
GET /agent/summary the last finished run's summary: verdict, layers, problems, overview, analysis
POST /agent/compare-signatures {document?, scenario?, schemes?, duration_s?}, GET the same runs one scenario under several signature schemes on a thread; GET reports progress and the result

The watcher reads run.status once a second and the run's evidence every few seconds; it never pauses, steps or changes a run.

Examples¶

# start a fixture server paused, then drive it over HTTP
v2xw-server --actors 50 --paused --no-agent &
curl -s localhost:8787/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"run.status"}'
curl -s localhost:8787/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"run.step","params":{"unit":"second","count":5}}'
curl -s localhost:8787/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":3,"method":"scenario.schema","params":{"sections":["groups","statuses"]}}'
curl -s localhost:8787/rpc/schema > openrpc.json
