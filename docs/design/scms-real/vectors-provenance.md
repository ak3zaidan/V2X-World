# Vector corpus and oracle: provenance (WP-A0)

Status: built 2026-10-16 by the WP-A0 agent, which did not read the engine's Rust security code
(`crates/v2xw-sec`, `v2xw-node` `secure.rs`, `v2xw-proto`). Plan: `00-gap-analysis-and-plan.md` §4.2 WP-A0.

## 1. What is where

| Path | What |
|---|---|

| `crates/v2xw-sec/tests/vectors/oracle/*.json` | Vectors generated by the oracle (`oracle.py emit`), with `MANIFEST.json` (sha256 per file) |

Run (one machine-wide heavy command at a time):

```
python3 -m venv <venv> && <venv>/bin/pip install asn1tools cryptography      # asn1tools 0.169.0, cryptography 50.0.2
.claude/pm/heavy.sh <venv>/bin/python -I tools/oracle/oracle.py selftest    # selftest: PASS (412/412 vectors in 27 checks)
```

Nothing is fetched at test time. The Rust tests read the JSON files only.

## 2. Sources and how each was transcribed

Values were copied by `tools/oracle/transcribe/transcribe.py`, never computed. Every IEEE and CAMP hex
value was cross-checked against the C-array repeat printed beside it in the source, so a wrapped or
mis-extracted line fails the transcription instead of entering the corpus. The oracle then
recomputes every value independently (`selftest`).

## 3. ASN.1 modules used by the oracle

`tools/oracle/asn1/ieee1609.2-2022/`: `Ieee1609Dot2`, `Ieee1609Dot2BaseTypes`, `Ieee1609Dot2Crl`,
`Ieee1609Dot2CrlBaseTypes` from the ETSI forge tag `2022-published` (commit `880216d33d08`, 2022-10-27),
<https://forge.etsi.org/rep/ITS/asn1/ieee1609.2/-/tree/2022-published>. They equal the official IEEE download
(<https://standards.ieee.org/wp-content/uploads/2023/02/1609.2-2022_downloads.zip>) modulo CRLF (checked by
hash after stripping CR). `Ieee1609Dot2CrlSsp`, `Ieee1609Dot2Peer2Peer` and `EtsiTs103097ExtensionModule`
are not on the forge tag and come from that IEEE zip, byte-exact (CRLF).
`tools/oracle/asn1/ieee1609.2.1-2022/`: the 14 `Ieee1609Dot2Dot1*` modules from the forge tag
`2022-published` (commit `329ff68846fe`, 2022-10-28), <https://forge.etsi.org/rep/ITS/asn1/ieee1609.2.1>.

Licence: neither forge repository carries a licence file and the IEEE zip has no licence text. This
follows the precedent of `third_party/asn1/etsi/ieee1609.2/` (committed from the same forge project);
the owner should confirm (open item 1). The engine's own copies under `third_party/` are untouched;
the oracle keeps separate copies so that it does not share inputs with the Rust build.

asn1tools 0.169.0 needed three adjustments, all in `scms_oracle/coer.py`:
1. information-object-class type fields (`CLASS.&Type`, used only for open types) are compiled as an
   unconstrained OCTET STRING, which is the OER encoding of an open type (X.696 clause 30);
2. the extension-addition presence bitmap was written shifted when a non-OPTIONAL addition was absent,
   and its unused-bits octet was 8 instead of 0 for a multiple of 8 additions (both fixed);
3. a named-bit DEFAULT on a fixed-size BIT STRING (`eeType DEFAULT {app}`, SIZE (8)) was sized to 1 bit.
Defect 2 and 3 were found by re-encoding the published SCMS Manager files; after the fixes they
re-encode byte for byte (§5).

## 4. Findings recorded while transcribing

- **ECIES P1 erratum (02 §8.2) confirmed.** In 1609.2a D.6.2 and CAMP `ecies.txt` the printed P1 of every
  vector equals the AES key k. The real P1 is in CAMP `ecies.py` (`p11` line 119 for vectors 1–2, `p12`
  line 125 for 3–4). With the real P1 all four D.6.2 vectors and all four CAMP vectors reproduce V, C and
  T; with the printed P1 none does (`selftest` checks `ieee-d6.2-erratum` and `camp-ecies-erratum` assert
  the failure). The corpus carries both (`in.p1`, `p1_printed`).
- **D.6.4 KDF2 outputs** are not recoverable from the PDF text, and the dl line of vector 4 is missing.
  The four D.6.4 input sets are identical to NIST CAVP `ansx963_2001.rsp` `[SHA-256]` entries, whose
  outputs are used (cited per vector) and equal CAMP `kdf.py` `known_key1..4`.
- **D.6.3 MAC1** inputs are the RFC 4231 test cases 1–7; outputs equal RFC 4231 truncated to 128 bits.
- **CAMP `glv.txt`** labels the encrypted-index input "j || k || 0^64" but prints k || j || 0^64. The
  corpus keeps the printed bytes and says so.
- **CAMP `implicit.txt`** is SEC 4 algebra with the illustration encoding CertU = tbsCert || compressed(P_U)
  and e = SHA-256(CertU) >> 1. It is not the 1609.2 profile. The oracle checks it in a separate SEC 4 mode.
- **Published SAESOL ACA certificate** (SCMS Manager test chain, file sha256 `9dbc552e…414c`): its
  ToBeSignedCertificate extension bitmap is encoded `02 06 80` (2 additions) where the 2022 module has 4
  (`02 04 80`). The ICA signature verifies over the canonical 2022 re-encoding. The engine must
  canonicalise before hashing and must accept such encodings on decode.

## 6. Open items

1. Licence of the 1609.2 / 1609.2.1 ASN.1 copies (same status as `third_party/asn1/etsi/ieee1609.2/`).
2. No public 1609.2-profile ECQV vector exists (02 §14). The oracle's ECQV-1609 is checked by the e formula
   against a direct hashlib computation, by key relations, and by reconstruction of its own certificates.
   The published chains contain no implicit certificates, so the real-world ECQV check of WP-A5 needs a
   pseudonym or implicit certificate from a provider.
3. Chain validation implements PSID/opaque-SSP coverage, eeType, chain length, validity, identifiedRegion
   country containment, signatures and the CTL anchor. Bitmap SSP ranges and geometric region containment
   are reported as unsupported, not passed.
4. The 2025 edition is not compiled by the oracle yet (`coer.EDITIONS` has only `2022`).
5. ~~OpenSCMS butterfly encryption vector (i = 7590, j = 0) is not in the corpus.~~ Added by WP-A4 (§9).
