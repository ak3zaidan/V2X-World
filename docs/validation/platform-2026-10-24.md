## Fixed

1. **A fixed BSM rate below 1.67 Hz was sent at 1.67 Hz.**
   - **Cause:** `wiring::generator_params` sets the fixed period as the BSM generator's nominal interval. The generator clamps its interval into J2945/1's [vMinITT, vMaxITT] = [100, 600] ms. The code lowered vMinITT for rates above 10 Hz but never raised vMaxITT.
   - **Effect:** at 1 Hz (the low end of the setting's range, which the catalogue sweep uses) the run sent a BSM every 600 ms.
   - **Fix:** vMaxITT rises to a fixed period above it. vMaxITT is the ceiling that J2945/1 congestion control may stretch to, not a floor under a rate the scenario fixed.
   - **Test:** `platform_validation::a_fixed_bsm_rate_is_the_rate_sent_across_its_range`.
   - **Goldens:** none move. No shipped scenario fixes a rate below 1.67 Hz.
2. **A SPaT or MAP period off the 100 ms node-step grid was rounded up.**
   - **Cause:** `MessageSchedule`'s periodic timer restarted from the instant of the check that sent the message.
   - **Effect:** every interval became a whole number of node steps: 150 ms became 200 ms (5 Hz instead of 6.7 Hz), and 250 ms became 300 ms. A unit clock running slow by a few ppm would also have skipped every other 100 ms check.
   - **Fix:** the timer now anchors on the instant the previous message was due. A unit that falls more than one interval behind restarts from now rather than bursting.
   - **Tests:** `v2xw-node generate::tests::a_spat_period_off_the_check_grid_keeps_its_rate`, `a_slow_clock_does_not_halve_the_spat_rate` and `a_roadside_unit_sends_spat_at_ten_hertz_and_map_at_one`.
   - **Goldens:** none expected to move. With exact clocks and 100 ms periods the anchored rule fires at the same checks as the old one.
   - **Not verified by a run:** the fixed-build re-runs of the determinism digests and `rsu-apps.yaml` were not done (lock contention). `bsm_timing` and `scms_scale` are the golden tests to run before merging.

## 3. Seed spread

Each family was run on 5 seeds (the default `0xC0FFEE_5EED` and 1–4). The interval is the 95 % t-interval of the mean (n = 5, t = 2.776), given as a half-width relative to the mean.

- **Radio family (`dsrc-grid`).** Tight: prr ±1.8 %, aoi ±3.3 %, cbr ±4.6 %, range90 ±8.4 %. The default seed's documented values sit inside every interval. e2e is the one exception: 12.453 ms against [12.36, 12.45], just at the edge.
- **`access_ms` (±122 %).** It is a handful of contention events per run. A row should never compare it across seeds with a 1 % band.
- **Security family (9 vehicles).** About ten times wider: aoi ±75 %, prr ±30 %.
  - Several `security-network.yaml` rows are single-seed effects smaller than this spread, for example a lower pseudonym period giving aoi +46 %.
  - They pass because base and change share a seed (common random numbers). Their *magnitude* should not be quoted without seed replicates.
- **Fault check.** A different seed must move every digest (row DT.threads.D control), so the seed reaches the run.

## Open

1. **Seed replicates for the security rows.** Replicate the security-network rows over at least 5 seeds before quoting their magnitudes (see 3).
2. **Spec mode does not measure everything the catalogue does.**
   - `traffic.*` exists only in `sensitivity/sweep.rs`, and `metric.verify_rate` / `metric.full_cert_share` only when the family records `metrics: [all]`.
   - A spec row naming one of these can never pass. The loader should refuse such a metric name rather than measure `None`.
3. **The Studio e2e `settings.spec.ts` is stale against the sectioned settings window.** It counts every `[data-testid=setting]` on the page (4 visible in the Run section of 398). The spec needs updating; the engine is not at fault.
4. **MAP is always certificate-signed.** Every MAP carries the unit's certificate (80 of 80), while SPaT follows `full_cert_every_ms`. That is plausible, since a receiver meets an intersection through its MAP, but no row pins it to a CTI 4501 or RSU-specification clause.
5. **BSM rate quantisation.** The BSM generator also restarts from each check's instant. It is checked at the fixed period when `rate_hz` is set, so it is exact there. Without `rate_hz`, a `messages.generator` `nominal_itt_ms` off the 100 ms step would round up, as SPaT did. Not changed: it would need a golden check on every BSM scenario.
6. **Thread speed-up is small on the 40-vehicle families.** The node phase is sequential (ObuRuntime is not `Send`), as `run.rs` documents.
