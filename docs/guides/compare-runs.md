# Comparing two runs

Run a scenario, change one setting, run it again, then press **Compare with previous** in the
header. You can also open it from the run summary, or from the Runs tab, where any two runs can be
compared.

## What the comparison shows

1. **What changed in the settings.** Every setting that differs between the two runs, labelled the way the settings window labels it. The seed is reported separately, and `meta` (the name and description) is left out.
2. **Main differences.** A few plain sentences that the engine writes. They are computed, not generated by an LLM.
3. **The metric overlaid over time** for whichever row you select.
4. **The metrics table.** Each row gives the previous value, the current value, the change, the % change and the health level on both sides. A change is coloured better or worse according to the metric's direction: the health band's `better` when the metric has a band, otherwise the Studio's polarity table. The table shows only meaningful changes unless you tick *Show all*. Rows are sorted with the meaningful ones first, then those that crossed a health band, then by size of change.

**Ask the agent** hands both run ids, the settings diff and the meaningful rows to the agent. The
agent's tools include `runs.compare` (it reads them from the OpenRPC document). **CSV** and
**Markdown** download the same table.

## How each value is computed

Each run is reduced to a digest (`v2xw/run-digest/1`) when the next run starts. The engine keeps
the last eight. Every headline metric in the digest is pooled over the run's windows the same way
`compare-signatures` and the experiment runner pool them:

- proportions pool their counts;
- ratios of sums pool both sums;
- scalars and distributions use a sample-weighted mean of each window's figure, so p95 is the p95 of a typical window;
- counts are summed.

A change is **meaningful** when either of these holds:

- it crosses a health band;
- it is at least 10 % of the baseline and larger than the unit's resolution.

If the two runs used **different seeds**, the change must also be larger than twice the combined
standard error. That error is estimated per run by batch means over the run's windows, with up to
10 batches (Law & Kelton, *Simulation Modeling and Analysis*, 5th ed., §9.5.3). If the runs used
the **same seed**, they share every random draw the settings did not touch, and the page says that
the differences come from the settings change.

## From the command line

```text
v2xw compare runs/base runs/tx10              # two `v2xw run --out` directories
v2xw compare prev.digest.json runs/tx10       # a digest saved from the Runs tab (Save) or runs.digest
v2xw compare a1,a2,a3 b1,b2,b3 --markdown     # replications: mean ± standard error across them
v2xw compare runs/base runs/tx10 --all --csv
```

Each side can be one of three things: a run directory, a digest file, or an experiment output
directory, whose `runs/*` are pooled as replications. You can also give comma-separated
replications. When replications are pooled, the noise test uses their standard error.

## RPC

| Method | Params | Result |
|---|---|---|
| `runs.list` | — | the current run and the previous ones, each with a `ref` (`current`, `previous`, run id) |
| `runs.compare` | `a` (default `previous`), `b` (default `current`): a ref or an inline digest; `format`: `json`, `markdown`, `csv`, `text` | `v2xw/run-comparison/1` |
| `runs.digest` | `run` (ref), `metrics` (only these series kept) | `v2xw/run-digest/1` |

The implementation is in `crates/v2xw-server/src/compare.rs`. The Studio, the agent and the CLI all
print its output.
