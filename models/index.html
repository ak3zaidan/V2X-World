Models overview¶

Every behaviour the engine simulates (a car-following law, a path-loss model, a codec, a detector, an emission model) is a model: a Rust implementation of a family trait plus a model card that states what it computes, from which parameters, with which sources, and where it is known to be wrong. A model without a card cannot be registered, and a number a model reads without declaring it on its card is a conformance failure.

Code: crates/v2xw-core/src/{model,card,registry}.rs, crates/v2xw-engine/src/scenario/publish.rs (slots(), models()), crates/v2xw-engine/src/wiring.rs (what a run registers). Every card in the published catalogue, with every parameter: Model parameters.

Families and slots¶

A family (v2xw_core::card::Family) is one seam of the architecture: a trait that extends Model, a conformance suite and a Python base class. The set is closed; adding a family is an engine change.

Area Families
world and traffic world, mobility, vru, weather, gnss, clock
radio propagation, fading, obstacle, phy, mac, dcc
network net, fragmenter, backhaul, cellular, backend-net
messages codec, generator
security envelope, primitive, crypto-backend, verification-policy, hardware-profile
applications and sensing safety-app, perception
credential system protocol, service-model, responder
threats attacker, detector, ma-pipeline
measurement metric, exporter
energy emission, energy

A slot is a place in the scenario where a model of one family is chosen. Most slots take a ModelChoice:

net:
  fragmenter:
    id: fragmenter/generic-sdu        # the card id
    params: {}                        # overrides of the card's defaults
energy:
  ev_model: energy/ev/vt-cpem         # a slot that takes a bare id

ModelChoice { id, params } denies unknown fields. Anything not named in params keeps the card's default, so the resolved parameter set is a pure function of the card and the overrides and can be content-addressed. The slot table (path, family, selectable ids and whether the engine acts on it) is generated: Slots.

Some models are chosen by named settings rather than an id slot: the radio stack by radio.rat, radio.tiers and radio.models (Radio and network), the signature scheme by security.signature (Security), the pseudonym policy by security.pseudonym_change.strategy (Privacy).

Resolving parameters¶

ParamSet::resolve(card, overrides) builds the parameter set a model runs on:

  1. start from every parameter's card default;
  2. null overrides keep the defaults; anything but a JSON object is refused;
  3. each override must name a declared parameter (a typo is an error listing the declared names, never a silent fallback), have the default's JSON type, and lie inside the declared range when there is one.

Resolved sets are interned in a ParamSetStore by SHA-256 of their canonical JSON, so provenance records point at a parameter set by id instead of copying it.

The registry¶

v2xw_core::Registry holds one registration per model id:

Field Meaning
card the card as registered
licence Apache-2.0, MIT, BSD, MPL-2.0 may be linked in process; GPL, LGPL or an unknown licence must run out of process
hosting in-process (Rust trait object, or batched Python via PyO3) or out-of-process (a separate process; its replies are hashed into the run digest instead of its code being linked)
content_hash SHA-256 of the card's canonical JSON

A ModelRef is a dense u32 handle in registration order, cheap to copy into provenance. Registering a different card under an existing id is refused. A hosted (out-of-tree) plug-in's card must target the engine's plug-in API version (same major; same minor while the major is 0).

The run's manifest pins every registered model as id@version with its card hash, so a changed default is a different run. A run registers what it composes (wiring::register_all, plus the radio models it builds, wiring::register_radio); the published catalogue (publish::catalogue) registers every crate that offers cards, so the documentation can list what a scenario could name.

The model card¶

v2xw_core::card::ModelCard:

Field Content
id stable id, ^[a-z0-9][a-z0-9-]*(/[a-z0-9-]+)*$, e.g. mobility/car-following/idm
family, version, api_version the seam, the model's semver, the plug-in API it targets
tier the fidelity tiers it implements (never empty)
purpose what it is for
equations each with a name, LaTeX or text, and notes on validity and units
parameters every number it reads: name, unit, default, optional range, source, calibration plan
assumptions what it assumes of the world or its inputs
limitations where it is known to be wrong or inapplicable
ignores what this tier leaves out relative to the next one up
sources citations for the model as a whole
validation status (unvalidated, unit-tested, literature-checked, field-checked), references, test names
determinism whether it draws random numbers and from which RNG domains
cost optional per-call cost estimate

Sources and todo: calibrate¶

Every parameter carries a Source of one kind: standard (a clause), paper, datasheet, dataset, code (another implementation), or todo-calibrate: a value the implementer chose that still needs calibration. A todo-calibrate parameter must carry a calibration plan (registry rule R1), and the generated reference lists them.

ModelCard::validate refuses, at registration, a card whose id is malformed, whose todo-calibrate parameter has no plan, whose parameter names repeat, whose default lies outside its own range (otherwise a scenario that never mentions the parameter would run on an impossible value), or whose version, API version, purpose or tier is empty.

How to read a card¶

On the generated page each card shows its purpose, version, tiers, hosting and whether it draws random numbers, then:

  1. Parameters: the table to override in params. Check the source column: standard and paper values are cited; todo-calibrate values are choices to vary in a sensitivity study.
  2. Equations: what the code computes, to check against the paper.
  3. Assumptions, Limitations, Ignores: what not to conclude from the model.
  4. Sources: what to cite.

Fidelity tiers¶

Tier Meaning Typical use
abstract closed-form or probabilistic stand-ins 10,000-node runs
medium the models the literature agrees on, without frame-level detail (the default) most studies
high frame-level or physically detailed a focus region or a small scenario

A scenario picks one tier per family (radio.tiers for the radio stack); a model that offers several branches on the tier selected. The validator refuses combinations that cannot compose, for example phy: high with mac: medium. At city scale, a microscopic focus region runs inside a mesoscopic network (scale, mobility/tiered/meso-micro).

Writing a model¶

use v2xw_core::card::{Family, ModelCard, Tier};
use v2xw_core::model::Model;

struct FreeSpace { card: ModelCard }

impl Model for FreeSpace {
    fn card(&self) -> &ModelCard { &self.card }
}

The family trait (pub trait Propagation: Model { … }) supplies the behaviour; Model supplies id(), version(), tiers() and family() from the card. Models reach the engine only through a narrowed context (v2xw_core::ctx::Ctx) that gives the clock, keyed RNG streams and the reads the family is allowed. Walk-through: Extending: models.
